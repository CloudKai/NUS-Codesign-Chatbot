### Item 2: first-call `needs_sources` flag (`f70a88f`, fix `550a176`)

**Setting.** `FAST_CHAT_NEEDS_SOURCES_ENABLED`, default `false`. Defined in `backend/settings.py` and documented (commented out) in `.env.example`. I confirmed the name in both files.

**What changed.**
- **Contract** (`agentcore_runtime/models.py`): `FastChatTurnOutput.needs_sources`, an optional boolean, not in `required`. Only JSON `true` counts; null, strings and omission read as `false`. `out_of_scope` clears it. The adapter passes it through the slim, nested and bare Q&A wire shapes. An older runtime or backend stays compatible.
- **Request** (`backend/domain.py`): a server-owned `CoachRequest.source_need_check`. `_prepare_authoritative_turn` always overwrites it, so a client value is dropped (tested).
- **Stamp rule** (`execution._wants_source_need_check`): the request is stamped only when the setting is on, the gate searched nothing, and no scope override applies. The overrides are Lecture Help, forced retrieval, stage status, stage progression, meta-guidance, a private-attachment question and a missing-image Q&A.
- **Backend prompt** (`backend/prompts/composer.py`): a SOURCE CHECK paragraph appended to the runtime rules for `fast_chat` policy only. AgentCore receives it as `trusted_instructions`. It says when to set the flag and to keep the first reply free of course-specific facts.
- **Runtime prompt** (`agentcore_runtime/prompts/fast_chat.md`, `structured_coach.py`): one bullet each saying the field is optional and deferring to the SOURCE CHECK rule. The static cacheable prefix therefore does not depend on the setting. No shared stage file changed, so `tests/domain/test_prompt_stage_drift.py` passes unmodified.
- **Provider** (`backend/agentcore_provider.py`): honours the flag only when `request.source_need_check` is true and, after `550a176`, only when the returned mode is Q&A.
- **Workflow, telemetry, mock provider.** `needs_sources` goes through the workflow orchestration dict. `source_need_check`, `fast_chat_needs_sources`, `fast_chat_needs_sources_ignored_coaching` and `rag_fallback_trigger` are added to `SAFE_PERF_FIELDS`. The mock provider gets a deterministic stand-in.
- **Eval** (`scripts/evals/evaluate_retrieval.py`): a `needs_sources_stubs` block with three stub models. First-pass gate numbers are unchanged.
- **Tests.** `tests/domain/test_needs_sources.py` (35 tests in the feature commit, 3 more in the fix commit) and extra cases in `tests/scripts/test_evaluate_retrieval.py`.

**Decisions and rationale.**
1. **`needs_sources` coexists with `needs_source_retrieval` and `_maybe_rag_fallback`; it does not replace them.** The plan said "replacing the second-call fallback". I departed from that on purpose.
   - A first-call flag can only say the answer was written without evidence. A second call is needed either way, so the new field replaces only the narrow trigger.
   - `needs_source_retrieval` is a required wire field in the deployed contract and has its own tests. It fires only when the student selected sources and hydrates personal sources only. It cannot reach the course catalog when nothing is selected, which is the case for all 76 remaining wrong skips.
   - `needs_sources` is the superset trigger. It hydrates selected sources plus the course catalog, works with nothing selected, and ignores `retrieval_required`.
   - Both share `_maybe_rag_fallback`, the two-invoke budget (`FAST_CHAT_MAX_PROVIDER_INVOCATIONS_PER_TURN`), the not-persisted-first-result rule and the idempotency claim. With the setting off, the old guards run in the old order. The old flag can be dropped later, once the new one has production data.
2. **Provider-level guard.** The flag counts only on a stamped request. A model that volunteers it, or text that induces it, cannot start a second call.
3. **Retry request.** It sets `retrieval_required=true` and `allow_model_knowledge=false` and clears `source_need_check`, so the retry cannot loop and a course turn fails closed like a first-pass catalog hit. If the retrieve raises a non-`ValueError`, the retry still runs with the "retrieval unavailable" context so the reply states the gap. `ValueError` (authorization or catalog integrity) always propagates.
4. **No retrieval source** (course library not synced, nothing selected): the first answer is returned unchanged. It is the brief reply the instruction asked for and may be model knowledge. This limit is documented and pinned by a test.
5. **Default off.** The real flag rate and over-flag cost cannot be measured offline. A flagged turn adds a Retrieve and a second model call. Every non-retrieving fast-chat turn gains about 600 characters of runtime rules. The AgentCore runtime must be redeployed with the field first, or the model never sees it.
6. **Field optional, not required.** A required field would break rolling deploys between backend and runtime.
7. **Coaching turns ignore the flag (review fix `550a176`).** See "Review findings" below. This keeps coaching behaviour identical to the setting being off.

**Review findings.** `.agents/tasks/phase3-work/` holds one review document, `item2-review.md` and `.json`, which is round 2 (verdict APPROVED). The round 1 review text was not kept as a file. Its findings survive only in the "Review round 1 fixes" section of `item2-notes.md`.
- **Round 1, blocking: no test for a flagged coaching turn whose retry sets `allow_model_knowledge=false`.** Resolved by changing behaviour, not by testing the retry. The provider now ignores the flag on a coaching turn, so that retry no longer happens. Two tests pin this. `test_flag_true_on_a_coaching_turn_is_ignored_and_keeps_the_first_turn` shows 1 model call, no retrieval, and the first reply, assessment and stay recommendation persisted. `test_mock_provider_flag_on_coaching_question_does_not_retrieve` covers the mock provider. I read both tests. No test asserts `allow_model_knowledge=false` on a coaching retry, because that path no longer exists for coaching. The Q&A retry is tested for retrieval scope and reply persistence (`test_flag_on_course_question_without_cue_retries_with_course_catalog`), and I found no test file that asserts `allow_model_knowledge=false` on the retry request itself.

## 7. Live runs that remain relevant (none were run)

**Live Knowledge Base eval.** The flags `--live-kb` and `--max-live-calls` exist in `scripts/evals/evaluate_retrieval.py` and in its `--help`. Both are required together. N must be 1 to 100. Without both, the script prints `refused: ...`, exits with code 2 and makes no call. Live mode also needs `KNOWLEDGE_BASE_ID` and `COURSE_MATERIALS_BUCKET` set, or it refuses. The env vars are those named in the Phase 2 report:

```bash
KNOWLEDGE_BASE_ID=<kb id> KNOWLEDGE_BASE_TYPE=managed \
KNOWLEDGE_BASE_METADATA_FILTER_MODE=required \
COURSE_MATERIALS_BUCKET=<course bucket> AWS_REGION=<region> \
  python scripts/evals/evaluate_retrieval.py --live-kb --max-live-calls 30 \
  --json-output /tmp/retrieval_eval_live.json
```

- Use `--max-live-calls 94` to cover all 94 questions. Below 94 the script takes an evenly spaced, deterministic subset.
- It makes one Bedrock `Retrieve` call per question, with no retries and no model call. A wrapper around the client raises when the count reaches the limit.
- **AWS and cost notes (from the Phase 2 report).** It makes real Knowledge Base calls and costs money, so run it only with your approval. It needs the Phase 0 settings and AWS credentials from the normal credential chain: the Knowledge Base id and type, the `required` filter mode, the course bucket and the region. `KNOWLEDGE_BASE_REGION`, if set, overrides `AWS_REGION` (verified in the script's `run_live`). The Phase 2 report names no specific IAM action and gives no price. The call needs permission to `Retrieve` on that Knowledge Base, which is my assumption, not a statement from the report.
- It reports material-level recall@4 and the empty-result rate. Page recall is `n/a`, because Knowledge Base results carry no page. The gate numbers stay offline. Phase 2 noted the live path itself has not been tested against AWS, so treat the first run as a check of the script too.

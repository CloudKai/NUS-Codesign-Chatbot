### Item A: live-model eval for `needs_sources` (`0f0e418`)

Files: `scripts/evals/evaluate_retrieval.py`, `tests/scripts/test_evaluate_retrieval.py` (27 new tests), `docs/RETRIEVAL_EVAL.md` (new section "Run the `needs_sources` eval against the live model"), `docs/RAG_ARCHITECTURE.md` (one sentence), `.env.example` (comment only), `tests/AGENTS.md` (table row). No file under `backend/` or `agentcore_runtime/` changed. **No new setting**: the mode reads `COACHING_MODEL_PROVIDER`, `COACHING_MODEL_ID` and `AGENTCORE_MODEL_REGION`.

How it works:
- `--live-model` needs `--max-live-calls N` (1 to 500). Without the cap the script prints `refused: ...`, exits 2 and makes no call. It also refuses when combined with `--live-kb`, when `COACHING_MODEL_PROVIDER` is not `bedrock`, when the model id is not a Haiku model, or when no region is set. I confirmed with `--help` that both flags exist.
- Backend half: `build_live_request` builds the `CoachRequest` that `_prepare_authoritative_turn` would stamp, then calls `AgentCoreCoachProvider._invoke_payload`. That is the production code that composes the runtime rules (including the SOURCE CHECK paragraph), plans history and builds the Converse messages. The AgentCore client is a stub that raises if used.
- Runtime half: `LiveFastChatBridge` uses the runtime's `specialist_system_prompt` (fast-chat prompt plus output contract), `conversation_for_invoke`, and the `FastChatTurnOutput` schema as one forced tool. The reply is parsed with the runtime parser and checked by the backend's `_validated_fast_chat`, so mode enforcement and the "Q&A turn only" rule for the flag are production code.
- All 295 gate messages are sent, one call each, with the row's own `history`. Below 295 an evenly spaced deterministic subset is sent.
- Stops after the first auth or access error. Exit codes: 0 completed, 1 every call failed, 2 refused before any call, 3 stopped early on an auth or access error after at least one success. The first failure's exception class and AWS error code go to stderr; the message body is never printed (a test checks it).
- Reports wrong-skip, false-retrieve, flag rate and extra calls, split by category, gate-only and with the model, on the same scored rows.

**Differences from production (documented in `docs/RETRIEVAL_EVAL.md`).** No guardrail, no prompt-cache point, no structured-output recovery turn (no tool call counts as a failure), no SDK retries. Strands is not installed in the backend venv, so the script calls Bedrock `converse` directly with the Pydantic schema (`$ref` inlined) rather than `fast_chat_invoke`. This also keeps the original exception class visible. The first live run is therefore also the first check that Bedrock accepts this tool schema.

## 5. What the numbers do and do not prove

**Offline gate and recall numbers (all items).**
- They prove that the three items did not change the first-pass gate, the ranking or the lexical recall. That is the intended result.
- They do not describe the real Knowledge Base. The recall and empty-result figures come from a lexical stand-in. The gate figures come from 295 **synthetic**, single-author messages, and the `skip` share (48%) is higher than real traffic. They are not production rates.
- The target from Phase 3 (wrong-skip under 25%, false-retrieve under 10%) is **still not met with `FAST_CHAT_NEEDS_SOURCES_ENABLED` off** (49.4% and 5.0%). With it on, only the stubs exist, which bound the result but do not measure Haiku. Item A is the tool that would measure it, and it has not been run.

**Item A.** The stub run is a plumbing check. It proves the request is built through production code, the cap, the stop rules and the metric composition behave as designed (including equality with the offline `mock_rule` row). It does not prove Bedrock accepts the tool schema, the real flag rate, the real cost or how Haiku follows the SOURCE CHECK wording. One open risk: only auth and access errors stop the run. A schema rejection would fail all 295 calls with the same error. Bedrock does not bill rejected requests, but the run would waste its time and print a first-failure class that shows the cause. If you want a cheaper guard, run a first pass with `--max-live-calls 5` (see section 8) before the full run.

**Item B.** The offline tests prove the pass-through: a page present in KB metadata reaches the chunk, the citation and the UI text, and a missing, malformed or zero page yields no page text without breaking old citations. They do not prove this KB returns a page, that the page is 1-based and matches the PDF index, or that the strongest chunk's page is the one the model used.

**Item C.** The verdict is only as strong as the stand-in. The lexical search may rank a bare "what are the axes?" differently from a real embedding-based KB. A live check was not part of this item and was not run. The result is sensitive to the attribution rule: the raw failure count (8 of 9) meets the first condition alone, and only the control (the same need as a normal question is also skipped) moves most failures out of "follow-up form". Using the query check alone, 3 of 9 fail (gm296, gm297, gm298), still below 5. Twelve cases from one author show a pattern, not a rate. If you want rewriting for topic-less one-liners like gm296 to gm298, that is a product decision to take with a live check, not a result of this eval. Nothing here argues for loosening the gate: 0 of 3 `skip` follow-ups were searched.

## 6. Cache placement of the `needs_sources` paragraph

**Answer: the SOURCE CHECK paragraph is in the per-turn, uncached part of the prompt, not the cached prefix.** The Phase 3b expectation ("in the cached part") does not hold. No prompt was changed.

Evidence (read from the code at `8ac923a`; I re-checked each line below):
1. `backend/prompts/composer.py:98` defines `_SOURCE_NEED_INSTRUCTION`. Lines 353-354 append it to the runtime rules only when `context.source_need_check` is true and the policy is `fast_chat`.
2. `backend/agentcore_provider.py:1812` sends `prepared.runtime_instructions` as the payload field `trusted_instructions` (`_TRUSTED_INSTRUCTIONS_FIELD`, line 123). FastAPI does not send the shared or stage text. The runtime loads those itself.
3. In the runtime, `agentcore_runtime/structured_coach.py:739-742` builds `fast_chat_system_prompt(topic, trusted) + "\n\n" + _FAST_CHAT_JSON_CONTRACT`. `fast_chat_system_prompt` (`agentcore_runtime/specialists/fast_chat.py`, around lines 72-88) starts with `fast_chat_static_prefix(topic)` and then appends the "application runtime rules are authoritative" header plus the `trusted` text.
4. `fast_chat_static_prefix` (`fast_chat.py:42-59`) holds only shared coaching, the stage prompt and `fast_chat.md`. Its docstring says runtime rules, student text and retrieved evidence are excluded.
5. `agentcore_runtime/structured_coach.py:779-806` (`agent_system_prompt`) sets `prefix = fast_chat_static_prefix(...)` and `suffix = assembled[len(prefix):]`. `agentcore_runtime/prompt_cache.py` returns `[{"text": prefix}, {"cachePoint": ...}, {"text": suffix}]`. Everything after the static prefix, including the SOURCE CHECK paragraph and the JSON output contract, is in `suffix` and is billed as uncached input.
6. The item notes also measured this with a payload carrying the paragraph: it is absent from the prefix block (23,108 characters for `problem_identification`) and present in the suffix block.

Related facts:
- **Size is 797 characters, not about 600.** I measured `len(_SOURCE_NEED_INSTRUCTION)` = 797 (about 200 tokens at the repo's 4 characters per token). The "about 600 characters" in the Phase 3 report, section 5, is stale. I did not edit that section.
- It is added only on turns where `_wants_source_need_check` (`backend/coaching/execution.py:271`) is true: the setting is on, the gate searched nothing and no scope override applies. The retry call omits it. With the setting off (the default, `backend/settings.py:374-375`) the cost is zero.
- A two-line pointer to the field is already in the cached prefix, in `agentcore_runtime/prompts/fast_chat.md`. It is there whether the setting is on or off. The wording that tells the model when to set the flag is only in the uncached suffix.

**Cost implication.** About 200 extra uncached input tokens per eligible first call. At Haiku 4.5 list rates ($1.00 per million uncached input tokens, $0.10 per million cache read, from a [third-party mirror of Anthropic's pricing table](https://anthropic-claude-docs.mintlify.app/zh-CN/docs/about-claude/pricing); confirm against the Bedrock price page) that is about $0.0002 per eligible turn, against about $0.00002 if it were a cache read. The gap is about $0.18 per 1,000 eligible turns. It is small next to the second model call a flagged turn already costs, and the paragraph is about 3% of the cached prefix size.

**Side finding (not asked, not investigated further).** The cache point is only emitted when the estimated prefix is at least 4,096 tokens (`prompt_cache.py:25, 156`). The item notes measured 5,777 estimated tokens for the five stage topics but 3,963 for `ethics_critical`, which is below the minimum, so that stage would get no cache point whatever `FAST_CHAT_PROMPT_CACHE_ENABLED` says. The estimator is conservative (4 characters per token), so the true count may be higher. I did not re-measure this.

**Proposed fix, for you to decide (nothing implemented).**
- **Option 0, do nothing (recommended for now).** The cost is about $0.0002 per eligible turn and the setting defaults to off. Revisit once the canary shows the real eligible-turn rate.
- **Option 1, move the guidance into the cached prefix.** Put the full SOURCE CHECK wording in `fast_chat.md` and send only a one-line trigger in the runtime rules (for example "SOURCE CHECK: active this turn"). The cached prefix grows by about 200 tokens and is billed at the cache-read rate. Per-turn text drops to about 15 tokens. Costs: both prompt copies need the same edit (drift test), the first request after any prompt edit pays a cache write at 1.25 times the price, and the model sees the guidance on turns where the flag is off, which is a behaviour risk and would need a re-check of the Phase 3 wording.
- **Option 2, reorder inside the suffix.** No saving, since the whole suffix is uncached. Not worth doing.
- Inserting the paragraph into the prefix only when the setting is on is not advised: it creates two different prefixes and splits the cache.

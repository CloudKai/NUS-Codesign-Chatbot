## 3. Item 1: coaching-mode greeting failure (commits `ec3d87f`, `fd7a6e2`, `860eced`)

**Why.** Live: 17 failed calls, all "coaching mode requires recommendation stay or advance". The model-facing tool schema already requires `recommendation` for coaching replies, but Haiku omitted it on greetings and thanks.

**What changed.** `FastChatTurnOutput.coaching_requires_recommendation` (`agentcore_runtime/models.py`) now returns a copy with `recommendation="stay"` when the mode is coaching and the field is absent, null or blank (`""`, `none`, `null`), and sets a private flag `recommendation_defaulted`.
- It never produces `advance`. An unknown token such as `maybe` still fails validation.
- Explicit `stay` and `advance`, Q&A (recommendation still forced to None) and out_of_scope handling are unchanged.
- The model-facing JSON Schema, both prompt copies and `tests/domain/test_prompt_stage_drift.py` are unchanged. No new setting; the fix is unconditional because the default is the non-advancing value and follows the same path as a model-sent `stay`.
- `adapt_fast_chat_turn_payload` keeps the legacy rule for a nested `assessment` with no top-level recommendation (otherwise a legacy nested `advance` would have been silently downgraded).
- Observability: wire marker `recommendation_defaulted: true` (only when defaulted), perf field `fast_chat_recommendation_defaulted` (`backend/turn_perf.py`), and in the live eval a per-row flag plus `recommendation_defaulted: {count, ids}`.

**Where the default lives, and why.** In the shared model, because the failure happens inside the runtime (Strands validates the tool input, retries once, then returns `structured_output_failure`; the backend re-invokes once; the student then sees "The answer was not confirmed saved"). A backend-only default never sees these replies. Consequence: **the fix reaches production only after `agentcore_runtime/` is republished.** A backend-only deploy leaves the failure in place.

**Stage safety.** Every consumer of the recommendation was read and tested (`tests/domain/test_fast_chat_recommendation_default.py`). A defaulted `stay` never auto-advances a stage and never bypasses confirmation. Review finding F1 (blocker): in Free mode (`response_detail=long`) `backend/workflow.py::_promote_free_mode_advance` turned a defaulted `stay` into `advance` plus a pending proposal. Fixed in `fd7a6e2`: `EducationalAssessment` carries an in-memory private flag (`recommendation_defaulted`, not a field, never persisted), and the promotion skips it. An explicit model-sent `stay` in Free mode is still promoted (unchanged behaviour). Proof the guard matters (script run): reverting the `workflow.py` guard fails 12 of the 45 tests then in that file.

**Review finding F2 (found open in this final step), fixed in `860eced`.** The reviewer (`review-item1.md`, CHANGES_REQUESTED) found that the notes' claim "a runtime-first deploy is safe" was false: the republished runtime sends `stay` plus the marker, and the Free-mode guard works only because a backend containing `fd7a6e2` reads the marker. An older backend ignores it and, in Free mode, would open a "Next" proposal on a defaulted greeting (the student must still confirm, so no stage changes by itself). Fix: deploy note corrected in `docs/IMPLEMENTATION_STATUS.md` and `docs/RETRIEVAL_EVAL.md` (deploy the backend containing `fd7a6e2` before or together with the runtime republish; reverting the backend alone reintroduces this); 4 new parametrised tests feed `structured_wire_payload(FastChatTurnOutput.model_validate(<no recommendation>))` through `CoachWorkflow` (graph and sequential) in Free mode at `concept_generation` and `deep_analysis` and assert `stay`, no readiness candidate and no pending transition. Result (script run): 49 passed in that file. I did not get a second review of `860eced`.

## 10. OPEN DECISION (described only, not implemented)

**Question.** Should answers on course Q&A turns where no search ran be labelled as "general, not from course materials"?

**Why it matters.** The gate still wrongly skips retrieval on roughly half of course-related questions (section 4: 76/154 on all 295 rows, 49.4% [41.6, 57.2]; Phase 3c live 51 to 62 of 109). When it skips, the model answers from broad knowledge with no course citation and nothing tells the student so. That is the gap behind the product rule in item 0.

**Where the signal is known in code (hand, read in this step).**
- `backend/coaching/execution.py`, in the turn-preparation method: `include_course_catalog` is decided around lines 3211 to 3227; `needs_retrieval` is final after the gate and the Laya override (around lines 3196 to 3276); `record_field("retrieval_required", ...)` at about 3279; `record_field("rag_used", bool(retrieved_chunks))` at about 3380; `source_need_check` is set at about 3382.
- At about line 3400: `allow_model_knowledge = not effective_source_ids and not include_course_catalog`. On a course question where the gate skipped retrieval, `include_course_catalog` is false and no source is selected, so `allow_model_knowledge` is **True**. This is the exact "no search ran" signal. It is passed to the provider request at about line 3446 and reaches `backend/prompts/composer.py`, where line 305 adds "Broader knowledge is allowed when sources do not answer the question."
- `_maybe_rag_fallback` (about lines 2679 to 2775) re-runs the turn with the course catalogue when the model flags `needs_sources`; it sets `allow_model_knowledge` false for the retry, so a retried turn would correctly carry no general-knowledge label.
- The response mode (`qa` versus coaching) is on the assessment (`response_mode`), which the React `Turn` type in `frontend/src/stream.ts` already carries. Citations are `assessment.citations`.
- Not known in code: whether a Q&A turn with no search is about the course. The gate decided "no retrieval", so there is no "this was a course question" fact. The label would be on every Q&A turn where `response_mode == qa`, `rag_used` is false and `allow_model_knowledge` is true.

**Smallest implementation (two variants).**
- **A, prompt only (smallest).** In `composer.py` at the `allow_model_knowledge` branch (line 305), when the expected mode is Q&A and no excerpts were retrieved, add one instruction: start the answer with a fixed sentence such as "This answer is general and not from your course materials." No schema change, no UI change, one prompt copy (and the stage-drift test must be checked). Weakness: the model can omit or rephrase it, and the signal is not available to the UI or to analytics.
- **B, deterministic field plus UI tag.** After the turn is built in `execution.py`, set a server-owned field (for example `grounding = "general"` when `response_mode == qa and not retrieved_chunks and allow_model_knowledge`, `"course"` when excerpts were used) on the assessment or turn metadata; persist it with the assistant message (the allow-list in `backend/persistence/store/contracts.py` around line 39 and the message persistence would need the key); return it on the existing `reply_ready` payload; render a small tag in `frontend/src/Conversation.tsx` (and the Streamlit view if it must match). Add the perf field next to `rag_used`. About one field, one persistence key, one UI element and tests (set/unset per branch, retry clears it, old messages without the field render nothing). This is the version I would choose if you decide yes, because the label does not depend on the model remembering to say it.

**Risks.**
- The label is a claim about provenance that the code cannot fully back: "general" means "no search ran", not "the model did not use course knowledge". A model might still paraphrase lecture content from earlier assistant replies (the prompt forbids it only when excerpts are required).
- It would also tag legitimate general or off-topic Q&A (about 5% false-retrieve rows are the opposite case and unaffected), which may read as noise or reduce trust in correct answers.
- It exposes the gate's miss rate to students: about half of course questions would be tagged. That may be the intended honesty, but it is also a visible quality signal and a product and research-interview decision.
- Copy and language: the sentence must follow `response_language`; a fixed UI string is simpler than a model sentence.
- Variant B adds a persisted field and a contract change on the stream payload (old clients ignore unknown fields on `reply_ready`, but only if the decoder tolerates extra keys; check `decode()` before shipping).
- It does not fix the cause (wrong skips). It only discloses. It does not implement the product rule's other half ("could not verify the course definition"), which needs the gate to identify a course concept question first.
- Interaction with Laya and `needs_sources`: both promote some turns to a search, so the label would shrink as those improve; the metric to track is the share of Q&A turns with `grounding = general`.

**Left to you:** whether to label at all, A or B, the exact wording, and whether it should appear in research exports.

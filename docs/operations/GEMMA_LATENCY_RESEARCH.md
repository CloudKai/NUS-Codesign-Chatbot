## Managed Mantle controls

- **Endpoint and context.** AWS lists a 256K-token context window and a 3.5 MB request-body limit, including visual input. Oregon supports in-Region inference through `https://bedrock-mantle.us-west-2.api.aws/openai/v1/responses` and the corresponding Chat Completions route. This model has no Geo or Global inference profile. The context window limits the sequence the model can handle. A 6,366-token prompt occupies only that many input positions. Lowering an app ceiling above the tokens already sent leaves the work for that request unchanged. Count the actual serialized input, including instructions, chat history, source excerpts, schema and multimodal content. [AWS model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-google-gemma-4-31b.html), [Google model card](https://gemma.ai/models/gemma-4/model-card/), [DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin).
- **Priority.** The model card explicitly lists Standard (`default` or omitted), Priority (`service_tier: "priority"`) and Flex (`flex`). Reserved is unavailable. AWS describes Priority as the faster premium tier and Flex as suitable for work that can wait. The Oregon Standard price is US$0.14 input and US$0.40 output per million tokens. Applying AWS's listed 75% premium gives US$0.245 and US$0.70 for Priority. At the smoke's token mix, this is about US$0.000953 versus US$0.001667 per single model request before any cache or other charges. Cutting input by 42.9% would offset the input-price premium alone. Check the actual served tier when reported, IAM eligibility and billing before estimating cost or attributing a speedup. Mantle IAM can restrict the requested tier. [AWS model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-google-gemma-4-31b.html), [AWS pricing](https://aws.amazon.com/bedrock/pricing/), [Mantle IAM reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_bedrock-mantle.html).
- **Prompt caching.** The AWS model card lists implicit caching on Mantle. AWS attempts eligible prefix reuse automatically and recommends putting stable content first and dynamic content last. Hits are best effort. Gemma's repository flag controls the runtime's explicit Converse `cachePoint` path, so the flag's false value supplies no evidence about Mantle hits. Keep static instructions, role/stage versions and schema serialization stable where possible. Capture cached input token counts if this route exposes them and treat missing fields as unknown. The existing telemetry reads Strands cache counters. Verify that the pinned SDK forwards any cache information for Gemma Responses before interpreting the counters. Gemma-specific minimum, TTL, hit rate and billing savings remain unverified. [AWS model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-google-gemma-4-31b.html), [AWS prompt caching](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html), [runtime cache code](../../agentcore_runtime/prompt_cache.py).
- **Reasoning.** AWS says both Gemma 31B APIs honor reasoning effort and only Responses returns reasoning content. The model card does not specify which effort values this variant accepts, its default or whether reasoning can be fully disabled. The repository sends a 2,048 output-token cap and no explicit effort override. Evaluate effort only as a separate change, especially on hard evidence and judgment cases. [AWS model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-google-gemma-4-31b.html), [runtime model settings](../../agentcore_runtime/model.py).
- **Batching and capacity.** AWS's asynchronous batch-job list includes Gemma 3 but omits Gemma 4 31B. Simultaneous independent Responses calls are online concurrency. The endpoint exposes no customer controls for GPU model or count, precision or FP4, scheduler batch size, or splitting prefill and decode. AWS recommends gradually ramping Mantle throughput and notes that this model's default limits are not surfaced directly through Service Quotas. Mantle's quota guide says the requested output maximum participates in input-rate reservation and excludes cache reads from input-token rate accounting. A smaller cap can help reservation pressure if it still fits the full response. At 80 hypothetical requests each using the smoke's input and the runtime default cap, the illustrative uncached reservation is `80 × (6,366 + 2,048) = 673,120` tokens. The direct burst used a different cap. No quota cause was established for its tail. [AWS batch support](https://docs.aws.amazon.com/bedrock/latest/userguide/batch-inference-supported.html), [AWS model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-google-gemma-4-31b.html), [Mantle quotas](https://docs.aws.amazon.com/bedrock/latest/userguide/quotas-mantle.html), [AWS throughput guidance](https://docs.aws.amazon.com/bedrock/latest/userguide/scaling-throughput-best-practices.html).

## Where latency can move

**Prefill** processes input tokens and prepares the attention KV cache. Longer uncached input typically adds compute before the first token. **Decode** then emits tokens sequentially and is often constrained by memory bandwidth. Reducing unnecessary reasoning or visible output can shorten decode. Streaming can show usable text earlier and still take the same time to reach validated, saved completion. A provider TTFT observed by the caller also includes network and service queuing. Capture first student-facing text separately from the first stream frame, JSON syntax or reasoning content. AWS currently publishes no Mantle equivalent of `InvocationLatency` or `TimeToFirstToken` in CloudWatch, so collect scoped clocks at the provider caller and browser. [DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin), [vLLM tuning](https://docs.vllm.ai/en/stable/configuration/optimization/), [Mantle metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-mantle-metrics.html).

## Accuracy-preserving experiment order

1. **Shorten static instructions first.** The three Problem Identification prompt source files total 23,080 bytes: 8,747 shared, 10,171 stage and 4,162 Fast Chat. These are source bytes. The wire request also carries runtime rules, schema and any history/source excerpts. The one-message smoke already used 6,366 input tokens. Consolidate repeat rules across shared/stage/Fast Chat and schema prose. Keep canonical schema validation, source identity, grounded citation and abstention rules, and confirmed stage progression. [Shared prompt](../../agentcore_runtime/prompts/shared_coaching.md), [Problem Identification prompt](../../agentcore_runtime/prompts/stages/problem_identification.md), [Fast Chat prompt](../../agentcore_runtime/prompts/fast_chat.md), [Gemma adapter](../../agentcore_runtime/gemma_responses.py).
2. **Tune evidence by relevance after measuring component sizes.** Repository defaults are a 16,000-token hard ceiling, 12,000-token soft telemetry threshold, six recent messages within an estimated 3,000 tokens, and up to four retrieval chunks within 8,000 characters. These are code defaults. Record effective deployment settings before drawing conclusions. Deduplicate overlapping excerpts and keep citation-bearing passages intact. Preserve recent corrections, project constraints, evidence for conflicting claims, and student-selected images or files needed by the question. Prefer a brief answer when the task allows it and validate complete strict JSON before lowering the output cap. [Settings](../../backend/settings.py), [model provider guide](../providers/MODEL_PROVIDERS.md).
3. **Change one factor per comparison.** Start with offline prompt assembly and the existing 50-case Fast Chat fixture across five stages. Its regression runner has a dry-run path and its live CLI is Claude-gated. For a separately authorized live comparison, use matched synthetic cases, same model/Region/schema/stream mode, and interleave control and candidate under comparable load. Measure input and output tokens, cached/reasoning tokens when returned, validation recovery, status/throttles, first provider content, browser first reply, saved completion and p50/p95/max cost and timing. Isolate prompt compaction, a stable-prefix comparison with a deliberately varied prefix, and Standard versus Priority on the same prompt. Include short, long, deeply sourced and multimodal turns. Compare grounded claims and citation IDs, abstention on missing or conflicting evidence, image understanding and file retrieval, pedagogical stage fit and confirmation, and schema/retry rates. [Fast Chat evaluator](../../scripts/evals/evaluate_fast_chat_regression.py), [evaluation corpus](../../tests/fixtures/fast_chat_quality_matrix.json), [classroom gate](CLASSROOM_CAPACITY_GATE.md).
4. **Verify the actual classroom path.** After quality passes, set acceptable queue time, browser time to first reply and durable completion thresholds with the owner. Exercise 80 independent synthetic users through admission, retrieval, guardrails, streaming, save/recovery and session cleanup under a separately approved cost cap. Compare concurrency versus arrival shaping and include queued/rejected and failed turns in reporting. Retain the existing rollback until this evidence supports a release decision. [Classroom gate](CLASSROOM_CAPACITY_GATE.md), [generation admission](../GENERATION_ADMISSION.md).

## Managed 26B-A4B comparator

Oregon also serves Gemma 4 26B-A4B on Mantle. Google lists roughly 3.8B active parameters for the mixture-of-experts model versus roughly 30.7B total in the dense 31B. At US$0.13 input and US$0.40 output per million tokens on Standard, the direct token-price advantage is small. Fewer active parameters make it a throughput and latency candidate, with the size of any improvement dependent on the serving implementation and workload. An equivalently grounded strict-schema comparison across stages and modalities is needed before any fallback decision. [AWS 26B-A4B model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-google-gemma-4-26b-a4b.html), [AWS pricing](https://aws.amazon.com/bedrock/pricing/), [Google model card](https://gemma.ai/models/gemma-4/model-card/).

## Self-hosted vLLM option

Start with a colocated BF16 baseline on the same `google/gemma-4-31B-it` checkpoint. vLLM lists an 80 GB NVIDIA GPU minimum for BF16 in its recipe and also shows a two-GPU tensor-parallel configuration. That is a starting configuration rather than a sizing claim for 80 students or 256K contexts. Size actual GPU/KV capacity from the response-length and prompt-length distribution. Tune continuous batching through `max_num_seqs`, chunked prefill and `max_num_batched_tokens`. Prefix caching reuses work only for matching input prefixes and cannot accelerate new token generation itself. The Gemma vLLM chat template supports `enable_thinking` plus a model-specific reasoning parser. Those template settings belong to the self-hosted stack. [vLLM Gemma 4 recipe](https://docs.vllm.ai/projects/recipes/en/stable/Google/Gemma4.html), [vLLM tuning](https://docs.vllm.ai/en/stable/configuration/optimization/), [prefix caching](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/).

LLM Compressor publishes a calibrated Gemma 31B NVFP4 recipe that leaves the vision and audio modules out of quantization. Native weight-and-activation FP4 acceleration depends on Blackwell kernels. On supported older NVIDIA GPUs, weight-only fallback retains 16-bit activations. Try BF16 and a supported intermediate FP8 baseline before selecting a calibrated FP4 variant. One upstream 31B GPTQ-MSE variant retained 99.6%, 99.3% and 99.4% of BF16 scores on GPQA-Diamond, MMLU-Pro and LiveCodeBench v6. The same sweep reports lower recovery for other variants, no repeat-seed uncertainty and no throughput measurement. Test the chosen checkpoint and hardware on coaching, citations and visual evidence separately and budget GPU idle time, operations and failover. [LLM Compressor Gemma 4 NVFP4 recipe](https://docs.vllm.ai/projects/llm-compressor/en/latest/key-models/gemma4/nvfp4-example/), [hardware and schemes](https://docs.vllm.ai/projects/llm-compressor/en/latest/guides/compression_schemes/), [upstream accuracy sweep](https://docs.vllm.ai/projects/llm-compressor/en/latest/research/nvfp4-sweeps/nvfp4-gemma4-agentic-sweep-dsikka/).

vLLM supports the matching Gemma 4 31B assistant checkpoint for multi-token prediction. This is a speculative decoding option for inter-token latency. Benchmark its effect on finished turns at intended concurrency once measurement identifies decode as a bottleneck. [vLLM multi-token prediction](https://docs.vllm.ai/en/latest/features/speculative_decoding/mtp/).

Only consider disaggregated prefill and decode after a colocated run shows that prefill interferes with tail token delivery under load. Separate vLLM workers can tune the phases independently but add KV transfer, duplicate model residency and interconnect demands. vLLM labels the feature experimental and tracks Gemma 4 asymmetric tensor parallelism with NIXL as work in progress. Validate the exact model, quantization, KV dtype, connector version, multimodal inputs and topology. Compare successful turns within both latency targets per dollar with the colocated baseline. [vLLM disaggregated prefill](https://docs.vllm.ai/en/latest/features/disagg_prefill/), [NIXL compatibility](https://github.com/vllm-project/vllm/blob/main/docs/features/nixl_connector_compatibility.md), [Gemma 4 NIXL tracking](https://github.com/vllm-project/vllm/issues/40017), [DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin).
